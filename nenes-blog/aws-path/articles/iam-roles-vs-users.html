IAM users vs roles: who gets which keys?

IAM decides who can do what in your account. The key habit: give people the least access they need, and give workloads roles instead of keys.

The four building blocks

ConceptWhat it is
UserA long-lived identity for one person or app, with its own credentials
GroupA collection of users that share the same permissions
RoleAn identity that anything trusted can assume for a short time
PolicyA JSON document that allows or denies actions on resources

Why roles matter

When something assumes a role, AWS issues temporary credentials that expire automatically. An EC2 instance, a Lambda function, or a person from another account can use a role without a stored access key. If temporary credentials leak, they stop working soon. A leaked long-term key keeps working until someone notices.

Reading a policy

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": [
      "arn:aws:s3:::example-bucket",
      "arn:aws:s3:::example-bucket/*"
    ]
  }]
}

This grants read-only access to a single bucket. Nothing else is allowed, because everything is denied by default.

How a decision is made

  1. Everything starts as implicitly denied.
  2. An Allow in an applicable policy can open an action.
  3. An explicit Deny always wins over any Allow.

Habits worth building

  • Apply least privilege: start narrow and add access when needed.
  • Do not use the root user for daily work, and protect it with MFA.
  • Prefer roles for applications and cross-account access.
  • Put users in groups, then attach policies to the group.
