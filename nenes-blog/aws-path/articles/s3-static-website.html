Host a static website on Amazon S3

Upload a few files to a bucket, turn on website hosting, and see exactly which permissions decide whether the world can read them.

What you are building

A static website is made of files that never change on the server: HTML, CSS, JavaScript, and images. Amazon S3 can serve those files directly from a bucket, so there is no server to manage.

Direct S3 website endpoints use HTTP, not HTTPS. That is fine for a lab. For a real site, put CloudFront in front of a private bucket.

1. Create a bucket

Open the S3 console and choose Create bucket. Bucket names are globally unique, so pick something specific like aws-path-lab-yourname. Choose the Region closest to you and leave Block Public Access on for now.

2. Upload the site files

Upload index.html, the CSS and JavaScript files, and every folder, keeping the same structure. Links such as articles/networking-cidr.html only work if the folder path matches.

3. Enable static website hosting

  1. Open the bucket, then the Properties tab.
  2. Scroll to Static website hosting and choose Edit.
  3. Enable hosting and set index.html as the index document.
  4. Save, and note the website endpoint shown at the bottom of the section.

4. Allow public read access (lab only)

Visitors are anonymous, so the objects must be readable by everyone. This needs two changes: turn off Block Public Access for this bucket, then add a bucket policy. Account-level or organization-level settings can still block this, which is a good thing in real accounts.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PublicReadForWebsite",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*"
  }]
}

Replace YOUR-BUCKET-NAME with your bucket. Note that the action is s3:GetObject only. Never grant public write access.

5. Test the endpoint

Open the endpoint URL from step 3. Then click through every page, check that the CSS loaded, and try the search and filters. If you see 403 Forbidden, re-check the bucket policy and Block Public Access. If you see 404, check that the index document name matches the file exactly.

Going further

For HTTPS and better control, use CloudFront with a private S3 bucket and Origin Access Control. Visitors reach the site through CloudFront, and the bucket never needs to be public.

Clean up

When the lab is finished, empty and delete the bucket so nothing is left behind. Confirm first that it holds no files you still need.

Check your understanding
  1. Why must the files keep their folder structure when uploaded?
  2. Which two settings must both allow access before an anonymous visitor can read an object?
  3. Why is the website endpoint not enough for a production site?

Answer them in your own words, then compare with the linked AWS documentation.
